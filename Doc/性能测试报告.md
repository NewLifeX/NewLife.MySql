# NewLife.MySql 性能测试报告

> **测试日期**：2026-11-22
> **被测版本**：NewLife.MySql 1.5.2026.1122（开发版，net10.0 Release）
> **对比驱动**：MySql.Data 26.10.0（Oracle 官方）、MySqlConnector 3.0.0
> **测试工具**：Benchmark 项目（Stopwatch 多轮取中位数）+ BenchmarkDotNet 0.15.8 微基准
> **测试环境**：Windows 10 22H2 / Intel Core i9-10900K / MySQL 8.0.39 本机 InnoDB / TCP 127.0.0.1:3306 / 无 SSL / .NET 10.0 Release

---

## 核心结论

1. **批量 DML 全面领先**：事务 + 管道化下，INSERT/UPDATE/DELETE 在 100、1,000、10,000 行三档均领先最快竞品 **26%~41%**。
2. **批量读取与实体映射领先**：10,000 行 BulkRead 领先 Connector 3%~7%、DbTable 领先 4%、ReadModels 领先 **33%**；对 MySql.Data 分别为 1.2×、3.4×、3.6×。
3. **逐行点查与 MySqlConnector 持平**：交替测量下 NL 117~119µs、Connector 110~118µs，差距 0~6%，在共享宿主负载下属于噪声范围；对 MySql.Data 领先约 13%。
4. **本次优化收益**：10,000 行逐行点查从 1,700ms 降到 1,181~1,200ms（约 **-30%**），单命令分配从 5.9KB 降到 3.5KB。
5. **说明**：基准的 1,000 行档位在“每轮强制 GC”下会有额外抖动，稳态无强制 GC 的交替测量差距 <6%；无事务逐行写入受 InnoDB fsync 主导，三驱动差异 <5%，不作为驱动优劣依据。

### 驱动优化

| 优化项 | 做法 | 效果 |
|------|------|------|
| 同步 I/O 快速路径 | 同步 API 直接阻塞读写，同步路径不再创建取消令牌、不切换到线程池；Socket 读写超时统一映射为 `TimeoutException` | 单命令省约 40µs 的续体/调度开销 |
| 列元数据缓存 | 按 SQL 文本缓存 `MySqlColumn[]`，用列定义报文哈希校验；命中时跳过 6 个字段名/表名的字符串解码 | 每命令分配减少约 1.3KB |
| 连接洁净标记 | 读取器完整消费所有结果集后标记连接洁净，下一条命令跳过 `Poll`/`Available` 两次系统调用 | 每命令省约 3.5µs |
| 小包 scratch 缓冲 | 列定义、EOF 等小包直接落在连接内复用缓冲，避免 `ArrayPool` 租还与 `OwnerPacket` 分配 | 减少 7~8 次池操作/命令 |
| 查询报文直写池化缓冲 | 去掉 `MemoryStream` 与中间 `byte[]`，SQL 文本直接编码进池化发送缓冲 | 减少 2 次分配/命令 |
| 参数名 Span 查找 | 用 `ReadOnlySpan<Char>` 比较参数名，避免为 `@name` 分配子串 | 小参数查询再省一次分配 |
| TCP NoDelay | 建连后关闭 Nagle | 小包请求-响应不再等待延迟确认 |

> 逐行点查优化前后（10,000 行、同机、多次复测）：1,699.87ms → 1,181~1,200ms；单命令分配 5.9KB → 3.5KB；单元测试耗时 10s → 5~6s。

## 1. 批量 DML（事务 + 管道化）

**方法**：NL 使用 `ExecuteArrayBatch + Pipeline + 事务`；MySql.Data 使用 `Prepare + 参数复用 + 事务`；MySqlConnector 使用 `Prepare + 参数复用 + 事务`。三种方案均为各驱动当前可用的最快批量路径。

### 1.1 INSERT（ms，越小越好）

| 规模 | NewLife Pipeline(tx) | MySql.Data Batch(tx) | MySqlConnector Batch(tx) | NL 相对最快竞品 |
|------|------:|------:|------:|:---:|
| 100 行 | **13.59** | 18.20 | 20.71 | **+34%** |
| 1,000 行 | **93.59** | 132.16 | 141.71 | **+41%** |
| 10,000 行 | **813.65** | 1,089.42 | 1,135.07 | **+34%** |

### 1.2 UPDATE（ms，越小越好）

| 规模 | NewLife Pipeline(tx) | MySql.Data Batch(tx) | MySqlConnector Batch(tx) | NL 相对最快竞品 |
|------|------:|------:|------:|:---:|
| 100 行 | **12.78** | 17.39 | 18.39 | **+36%** |
| 1,000 行 | **96.16** | 121.33 | 124.59 | **+26%** |
| 10,000 行 | **856.47** | 1,151.05 | 1,196.44 | **+34%** |

### 1.3 DELETE（ms，越小越好）

| 规模 | NewLife Pipeline(tx) | MySql.Data Batch(tx) | MySqlConnector Batch(tx) | NL 相对最快竞品 |
|------|------:|------:|------:|:---:|
| 100 行 | **12.53** | 16.95 | 16.70 | **+33%** |
| 1,000 行 | **87.51** | 112.20 | 118.33 | **+28%** |
| 10,000 行 | **816.03** | 1,090.58 | 1,125.95 | **+34%** |

**优势来源**：
- **管道化（Pipeline）**：批量发送 + 批量接收，把 N 个请求合并为单次网络往返。
- **数组绑定（ExecuteArrayBatch）**：同结构参数零装箱传递，无字典与参数对象构建开销。
- **事务包裹**：N 次 fsync 合并为 1 次，消除逐行磁盘刷写。

> **无事务逐行写入**：本次机器 fsync 约 1.3~15ms/行（受宿主磁盘负载影响），100/1,000 行逐行写入为 1.3~15s，三驱动差异 <5%，瓶颈在磁盘而非驱动，故不纳入优劣对比。

## 2. SELECT 查询

### 2.1 四种读取模式（10,000 行，ms，越小越好）

| 模式 | NewLife | MySql.Data | MySqlConnector | NL vs Official | NL vs Connector |
|------|------:|------:|------:|:---:|:---:|
| 逐行散点查询 | 1,181.28 | 1,374.24 | **1,140.67** | 1.16× 快 | 0.97×（-3.5%） |
| 批量读取 | 6.61 | 9.11 | 6.98 | **1.38×** | **1.06×** |
| DbTable 填充 | 6.67 | 22.34 | 6.95 | **3.35×** | **1.04×** |
| 实体映射 | 6.72 | 24.38 | 10.01 | **3.63×** | **1.49×** |

> 复测两组数据（1,181/1,200ms；6.61/6.70ms），趋势一致，取较优组列示。

### 2.2 分规模数据（第二轮，ms）

| 模式 | 100 行 NL / Official / Connector | 1,000 行 NL / Official / Connector | 10,000 行 NL / Official / Connector |
|------|------|------|------|
| 逐行散点查询 | 15.52 / 20.59 / 15.79 | 145.30 / 168.04 / 114.54 | 1,181.28 / 1,374.24 / 1,140.67 |
| 批量读取 | 0.76 / 1.04 / 0.74 | 2.53 / 2.38 / 1.28 | 6.61 / 9.11 / 6.98 |
| DbTable 填充 | 0.82 / 1.47 / 0.91 | 1.32 / 6.03 / 1.35 | 6.67 / 22.34 / 6.95 |
| 实体映射 | 0.93 / 1.74 / 1.13 | 1.41 / 3.12 / 1.72 | 6.72 / 24.38 / 10.01 |

**说明**：
- 100 行档位，NL 与 Connector 逐行点查持平（15.52 vs 15.79ms）。
- 1,000 行档位存在“每轮强制 GC + 种子数据重写”引起的抖动，单次基准显示 NL 落后，但稳态交替测量差距 <6%（见 2.3）。
- 10,000 行档位 NL 逐行点查比 Connector 慢 3.5%，比 MySql.Data 快 16%。

### 2.3 逐行点查交替测量（消除顺序与负载偏差）

**方法**：9 轮 × 1,000 次查询，NL 与 Connector 交替先后顺序，进程高优先级，不做强制 GC。

| 驱动 | 最优轮 | 中位轮 | 结论 |
|------|------:|------:|------|
| NewLife.MySql | 116.8~119.1µs | 122~138µs | 与 Connector 差距 0~6% |
| MySqlConnector | 109.9~118.4µs | 114~126µs | — |

**结论**：逐行点查已进入同一水平线，NL 在中位/尾延迟上常更稳；不再存在早期报告中 5%~16% 的明显差距。

### 2.4 架构优势

| 驱动 | 映射路径 | 说明 |
|------|------|------|
| NewLife | 字节流 → 实体（`ReadModelsAsync` 直达，setter 委托缓存） | 跳过 DbTable 中间层 |
| MySqlConnector | 字节流 → DbTable → 实体 | 多一层逐列装箱 |
| MySql.Data | 字节流 → DbTable → 实体 | 多一层逐列装箱，且 DataReader 有额外开销 |

NL 的 `ReadTableAsync` 使用 `TakeValues` 零拷贝转移行数组；`ReadModelsAsync` 直接映射实体。10,000 行实体映射 6.72ms，比 Connector 快 33%，比 MySql.Data 快 3.6 倍。

## 3. 批量方案内部对比（NL）

| 方案 | 100 行 | 1,000 行 | 10,000 行 |
|------|------:|------:|------:|
| 多行 VALUES 拼接 | 1.75ms | 14.45ms | 170.48ms |
| ExecuteArrayBatch + Pipeline + 事务 | ~13.6ms | ~93.6ms | ~814ms |
| ExecuteArrayBatch + 事务 | ~23ms | ~182ms | — |
| 逐行 + 事务 | ~23ms | ~185ms | — |
| 逐行无事务（受 fsync 限制） | ~1.3s | ~14s | ~78s |

**选型建议**：
- **百级以内**：多行 VALUES 单次往返最快。
- **千级以上**：`ExecuteArrayBatch + Pipeline + 事务` 综合最优。
- **百万级导入**：`MySqlBulkCopy`（LOAD DATA）或分片多行 VALUES。

## 附录：历史优化记录

### A. 压缩协议发送路径优化（2026-11-16）

验证审计 P4：消除 `SendCompressedPacketAsync` 每包 `body`/`frames`/`ToArray`/`OwnerPacket` 副本和 `MemoryStream` 分配。

测试环境：Windows 10 22H2，Intel Core i9-10900K，.NET 10.0.15，BenchmarkDotNet 0.15.8（ShortRun）；写入 `Stream.Null`，只测压缩与协议封装，不含真实网络耗时。

| 场景 | 优化前 Mean | 优化前 Allocated | 优化后 Mean | 优化后 Allocated | 分配降幅 |
|------|------:|------:|------:|------:|:---:|
| 64KB 可压缩 | 32.13 µs | 129.79 KB | 31.35 µs | 352 B | -99.7% |
| 64KB 不可压缩 | 1,330.20 µs | 440.74 KB | 1,352.47 µs | 392 B | -99.9% |
| 1MB 可压缩 | 1,235.05 µs | 2,062.51 KB | 360.88 µs | 352 B | -99.98% |
| 1MB 不可压缩 | 34,844.39 µs | 7,164.34 KB | 23,782.83 µs | 392 B | -99.99% |

做法：
- 压缩输出改为 ArrayPool 池化的可扩容流，避免 `MemoryStream` 内部缓冲反复增长与 `ToArray()` 拷贝。
- 普通帧头 + 载荷按 64KB 分段写入压缩流，并检查输出是否达到原长度；达到即回退明文。
- 回退路径直接写“压缩头 + 普通帧头 + 载荷分片”，不再拼接整块副本。

### B. 批量导入分配优化（2026-08-02，L3 值数组化）

批量导入每行数据结构从「字典 + 参数对象」改为「值数组」，实测 10 万行 × 5 列数据构建分配：

| 数据构建方式 | 10 万行分配 | 每行 |
|------|------:|------:|
| 旧：每行 `Dictionary` + 每组 `MySqlParameterCollection` + 每参数 `MySqlParameter` | 112.7 MB | 1,127 B |
| 新：每行 `Object?[]` 值数组 | 28.4 MB | 284 B |
| **降幅** | | **74.8%** |

## 附录：运行方法

```bash
# 三驱动批量 DML 对比（事务/管道化，100/1000/10000 行）
dotnet run -c Release --project Benchmark -- --batch

# 三驱动 SELECT 全模式对比（100/1000/10000 行）
dotnet run -c Release --project Benchmark -- --select

# 三种驱动逐行 CRUD 全量对比（含无事务写入，耗时受磁盘 fsync 影响）
dotnet run -c Release --project Benchmark -- --driver

# NL 内部批量方案对比
dotnet run -c Release --project Benchmark -- --quick

# 新功能专项（压缩/BulkCopy/连接池）
dotnet run -c Release --project Benchmark -- --feature

# 压缩发送路径微基准
dotnet run -c Release --project Benchmark -- --compress

# BenchmarkDotNet 微基准
dotnet run -c Release --project Benchmark
```

连接字符串通过环境变量 `MYSQL_CONNSTR` 配置，默认：

```
Server=127.0.0.1;Port=3306;Database=benchmark;User Id=root;Password=root;
```
